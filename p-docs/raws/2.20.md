**Ngày 20 — Transactional Outbox: không bỏ quên sự kiện sau khi commit**

Ngày 18 đã giúp consumer xử lý an toàn khi event bị giao lại. Ngày 20 giải quyết phía còn lại:

> “Execution đã cập nhật tiền và chứng khoán thành công, nhưng backend dừng trước khi phát event. Làm sao hệ thống phía sau vẫn nhận được thông tin?”

Bạn sẽ lưu **dữ liệu nghiệp vụ và event cần phát trong cùng transaction MySQL**, sau đó dùng worker giao event.

Đây là phần còn thiếu để chạy đầy đủ bài **C4 — worker restart của ngày 21**.

---

**1. Mục tiêu và thời gian học**

| Thời gian | Nội dung | Kết quả |
|---|---|---|
| 30 phút nghiệp vụ | Khoảng lỗi giữa commit và phát event | Hiểu Outbox giải quyết vấn đề nào |
| 30 phút kỹ thuật | Bảng outbox, worker, retry và xác nhận giao | Có thiết kế phục hồi rõ ràng |
| 30–60 phút thực hành | Dừng worker tại các điểm lỗi | Event không bị bỏ quên, projection không tăng trùng |

**Sản phẩm cuối buổi:**

- Transaction execution tạo thêm bản ghi outbox.
- Worker đọc event từ MySQL và giao cho consumer ngày 18.
- Worker restart vẫn tìm thấy event chưa hoàn tất.
- Giao lại giữ nguyên eventId.
- Consumer không cập nhật projection lần hai.

Phạm vi bắt buộc: **một worker hoạt động, event BUY `ExecutionApplied`, giao trực tiếp tới consumer**. Chưa cần RabbitMQ.

---

**2. Nghiệp vụ — 30 phút**

**2.1. Cách phát event sau commit có khoảng lỗi**

```text
Cập nhật OMS, tiền và vị thế.
→ Commit.
→ Phát ExecutionApplied.
```

Nếu backend dừng giữa hai bước cuối:

```text
Dữ liệu nguồn đã thay đổi.
Projection chưa biết.
Không còn dấu vết bền vững cho việc phải phát event.
```

Restart không tự biết event nào đã bị bỏ quên.

**2.2. Phát event trước commit cũng không đúng**

```text
Phát ExecutionApplied.
→ Consumer cập nhật.
→ Transaction nguồn rollback.
```

Khi đó projection phản ánh một giao dịch chưa được ghi nhận thành công.

**2.3. Cách Outbox xử lý**

Trong cùng transaction:

```text
Cập nhật nghiệp vụ
+
Lưu event cần giao
→ Commit
```

Sau commit:

```text
Worker đọc outbox
→ Giao event
→ Ghi nhận kết quả
```

Nếu cập nhật nghiệp vụ hoặc ghi outbox thất bại, cả transaction rollback.

AWS mô tả Transactional Outbox để giải quyết vấn đề ghi database và gửi thông báo sang hệ thống khác không cùng thành công. Event được lưu cùng transaction với dữ liệu nguồn, rồi được thành phần khác đọc để gửi đi. [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html?utm_source=chatgpt.com)

**2.4. Outbox không loại bỏ việc giao trùng**

Vẫn có tình huống:

```text
Worker giao event.
Consumer commit thành công.
Worker dừng trước khi đánh dấu đã giao.
```

Restart:

```text
Event vẫn đang chờ trong outbox.
Worker giao lại.
```

Vì vậy:

```text
Outbox: lưu bền việc cần giao.
Consumer dedup: ngăn tác động lặp.
```

Hai cơ chế phải đi cùng nhau.

**4. Event được lưu phải đủ và bất biến**

Tiếp tục contract ngày 18:

```json
{
  "eventId": "evt-day20-001",
  "type": "ExecutionApplied",
  "schemaVersion": 1,
  "aggregateId": "ord-day20-001",
  "aggregateVersion": 3,
  "occurredAt": "2026-10-23T03:00:00Z",
  "payload": {
    "accountId": "acc-020",
    "orderId": "ord-day20-001",
    "securityId": "sec-001",
    "executionId": "exe-day20-001",
    "side": "BUY",
    "quantity": 40,
    "price": "24900"
  }
}
```

Quy tắc:

- EventId được lưu một lần và giữ nguyên khi giao lại.
- Payload mô tả execution đã áp dụng.
- Không dựng lại payload bằng trạng thái order hiện tại lúc worker chạy.
- Không đưa access token hoặc mật khẩu vào event.
- `aggregateVersion` lấy từ phiên bản order sau cập nhật tương ứng.
- Duplicate execution không tạo thêm event outbox mới.

Nếu order đã khớp thêm hoặc đã hủy, event cũ vẫn phải giữ nội dung ban đầu.

**5. Database MySQL**

**5.1. Bảng outbox**

```sql
CREATE TABLE outbox_events (
    event_id VARCHAR(64) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    schema_version INT UNSIGNED NOT NULL,

    aggregate_id VARCHAR(36) NOT NULL,
    aggregate_version INT UNSIGNED NOT NULL,

    business_key VARCHAR(191) NOT NULL,
    payload JSON NOT NULL,
    occurred_at TIMESTAMP(3) NOT NULL,

    status ENUM(
        'PENDING',
        'DELIVERED',
        'FAILED'
    ) NOT NULL DEFAULT 'PENDING',

    attempt_count INT UNSIGNED NOT NULL DEFAULT 0,

    next_attempt_at TIMESTAMP(3) NOT NULL
        DEFAULT CURRENT_TIMESTAMP(3),

    last_error_code VARCHAR(100) NULL,
    last_error_message VARCHAR(500) NULL,

    created_at TIMESTAMP(3) NOT NULL
        DEFAULT CURRENT_TIMESTAMP(3),

    delivered_at TIMESTAMP(3) NULL,

    PRIMARY KEY (event_id),

    UNIQUE KEY uq_outbox_business (
        event_type,
        business_key
    ),

    INDEX idx_outbox_pending (
        status,
        next_attempt_at,
        created_at
    )
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

Business key đề xuất:

```text
BUY:<accountId>:<orderId>:<executionId>
```

Khóa này bổ sung bảo vệ chống tạo hai event cho cùng tác động nghiệp vụ.

**5.2. Ý nghĩa trạng thái**

| Trạng thái | Ý nghĩa trong demo |
|---|---|
| `PENDING` | Còn cần giao hoặc cần thử lại |
| `DELIVERED` | Consumer trực tiếp đã xử lý hoặc xác nhận duplicate hợp lệ |
| `FAILED` | Không thể tự tiếp tục theo chính sách hiện tại; cần kiểm tra |

Không xóa event chỉ vì thất bại.

Trong bài một worker, chưa cần trạng thái `PROCESSING` hoặc lease. Nếu thêm chúng sau này, phải xử lý được trường hợp worker chết khi đang giữ quyền xử lý.

**6. Ghi outbox trong transaction nguồn**

Pseudocode:

```ts
await unitOfWork.run(async (tx) => {
  await lockExecutionResources(tx, input);

  const existing = await findAppliedExecution(tx, input);

  if (existing) {
    return existing;
  }

  await orders.applyExecution(tx, input);
  await accounts.applyBuyExecution(tx, input);
  await positions.applyBuyExecution(tx, input);
  await settlement.createBuyObligation(tx, input);

  await outbox.append(tx, executionAppliedEvent);
});
```

Đây là minh họa trách nhiệm; dùng các service thực tế của project và giữ thứ tự khóa đã thống nhất.

**Điều bắt buộc:**

- `outbox.append()` dùng cùng transaction connection.
- Nó không tự commit.
- Lỗi ghi outbox làm rollback toàn transaction nguồn.
- API không phải chờ consumer cập nhật projection mới trả response.
- Không phát event ra ngoài trước commit.

Nếu execution đã được xử lý, đường replay không được tạo outbox mới chỉ vì phát sinh một eventId khác.

**7. Worker đọc và giao event**

**7.1. Cấu trúc đề xuất**

```text
src/modules/outbox/
  outbox.types.ts
  outbox.repository.ts
  outbox.worker.ts
  event-transport.ts
  direct-consumer.transport.ts
```

Interface transport:

```ts
interface EventTransport {
  deliver(event: DomainEvent): Promise<void>;
}
```

Trong demo, `deliver()` chỉ thành công khi consumer:

- Commit cập nhật mới; hoặc
- Xác nhận duplicate hợp lệ đã được xử lý.

Conflict hoặc payload không hợp lệ không được trả thành công.

**7.2. Truy vấn công việc đến hạn**

```sql
SELECT *
FROM outbox_events
WHERE status = 'PENDING'
  AND next_attempt_at <= ?
ORDER BY next_attempt_at, created_at, event_id
LIMIT 20;
```

Worker phải đọc từ MySQL sau mỗi lần khởi động, không chỉ dùng danh sách event trong RAM.

**7.3. Luồng xử lý một event**

```text
Đọc event đến hạn.
→ Kiểm tra ngân sách retry.
→ Ghi nhận bắt đầu lần thử.
→ Giao event ngoài transaction nguồn.
→ Nếu thành công: đánh dấu DELIVERED.
→ Nếu lỗi: ghi lỗi và lên lịch thử lại hoặc FAILED.
```

Không giữ transaction hoặc khóa tài sản trong lúc gọi transport.

Nếu consumer thành công nhưng cập nhật `DELIVERED` thất bại, event vẫn có thể được giao lại. Dedup ngày 18 bảo vệ tác động của consumer.

**7.4. Không để vòng poll chồng nhau**

Tránh:

```ts
setInterval(async () => {
  await pollAndDeliver();
}, 1000);
```

nếu một lần xử lý có thể lâu hơn chu kỳ.

Ưu tiên vòng lặp có `await`, chỉ chạy lần poll tiếp theo sau khi lần trước kết thúc.

Bản bắt buộc chỉ có một worker hoạt động. Không khởi động worker mới theo mỗi HTTP request, mỗi tab hoặc mỗi WebSocket connection.

**8. Đồng hồ và retry**

**8.1. Tách thời gian nghiệp vụ với thời gian worker**

| Thời gian | Nguồn |
|---|---|
| `occurredAt` | Thời điểm nghiệp vụ |
| `nextAttemptAt` | Đồng hồ worker |
| Timeout và backoff | Timer vận hành |
| Token expiry | Auth Clock |

Nếu Market Clock đang cố định ở 23/10 nhưng ngày máy chạy là 21/10, không dùng `occurredAt` tương lai làm điều kiện bắt đầu giao event.

`nextAttemptAt` phải dùng clock vận hành nhất quán với truy vấn worker.

Các session MySQL nên được cấu hình UTC cho dữ liệu thời điểm.

**8.2. Chính sách retry giả lập**

```text
Tối đa 5 lần thử.
Backoff tăng dần, có giới hạn.
EventId và payload giữ nguyên.
```

| Trường hợp | Xử lý |
|---|---|
| Kết nối tạm thời lỗi | Lên lịch retry |
| Consumer timeout, kết quả chưa rõ | Có thể giao lại; consumer phải dedup |
| Payload/schema không hỗ trợ | FAILED hoặc quarantine |
| Cùng eventId khác nội dung | FAILED, cần điều tra |
| Vượt số lần thử | FAILED, không xóa event |

Nếu worker chết sau khi đã tăng `attempt_count`, lần sau phải xử lý rõ trạng thái hết số lần thử; không để một event `PENDING` bị bỏ qua mãi.

`FAILED` nghĩa là cần can thiệp, không có nghĩa event đã được giao.

Khi vận hành cho retry lại:

- Giữ nguyên eventId và payload.
- Ghi audit lý do.
- Đưa về PENDING theo quy trình rõ ràng.

**9. Phân biệt xác nhận khi có broker**

Bài bắt buộc giao trực tiếp nên `DELIVERED` có nghĩa consumer đã hoàn tất.

Nếu mở rộng sang RabbitMQ:

```text
Publisher confirm:
Broker xác nhận nhận publish.

Consumer ACK:
Consumer xác nhận xử lý delivery.
```

RabbitMQ nhấn mạnh hai cơ chế này độc lập: publisher confirm không chứng minh consumer đã xử lý xong. [RabbitMQ](https://www.rabbitmq.com/docs/confirms?utm_source=chatgpt.com)

Vì vậy, khi thay transport phải cập nhật ý nghĩa trạng thái và cách quan sát:

- Đã publish tới broker.
- Đã được consumer xử lý.

Không dùng một cờ để ngụ ý cả hai nếu chưa có cơ chế xác nhận tương ứng.

**10.1. Tắt worker trước khi tạo execution**

Kỳ vọng:

- Nghiệp vụ nguồn vẫn commit.
- Event tồn tại trong MySQL.
- Projection chưa nhận event.

Khởi động worker:

```text
Projection quantity = 40.
Projection cost = 996.000.
Outbox = DELIVERED.
```

Không gọi lại execution handler để “giúp” worker.

**10.2. Dừng sau consumer commit**

Dùng fixture độc lập để tránh ảnh hưởng kết quả bài trước.

Điểm lỗi:

```text
Consumer commit.
→ Worker dừng trước mark DELIVERED.
```

Restart worker:

```text
Event được giao lại với cùng eventId.
Consumer báo duplicate.
Projection không tăng lần hai.
Outbox hoàn tất.
```

Muốn chứng minh restart thực sự, chạy worker ở tiến trình riêng và khởi động lại tiến trình đó. Nếu chỉ mô phỏng bằng exception trong test, ghi rõ giới hạn bằng chứng.

**10.3. Ghi outbox thất bại**

Chủ động gây lỗi ở `outbox.append()`.

Kỳ vọng toàn transaction rollback:

- OMS không tăng filled.
- Tiền không chuyển sang payable.
- Vị thế không tăng.
- Không có obligation mới.
- Không có outbox event đã commit.

Log tối thiểu:

```text

eventType
aggregateId
businessKey
attempt
```

Các chỉ số đơn giản:

| Chỉ số | Ý nghĩa |
|---|---|
| Số event PENDING | Công việc chưa hoàn tất |
| Tuổi event chờ lâu nhất | Độ trễ giao sự kiện |

Tuổi backlog nên tính từ thời điểm vận hành như `createdAt`, không lấy Market Clock cố định rồi suy ra độ trễ mạng.

Có thể bổ sung:

```http

GET /api/ops/outbox/:eventId
```

Các API này yêu cầu OPS theo ngày 16. Không cho khách hàng sửa payload hoặc tự đánh dấu `DELIVERED`.

**12. Các giới hạn cần hiểu**

**Một worker không tự bảo đảm mọi thứ đúng thứ tự.**

Nếu event A lỗi và được backoff, event B có thể được giao trước A.

Consumer BUY của ngày 18 đang cộng lượng và chi phí nên phạm vi này phù hợp với bài tập. Khi thêm SELL, correction hoặc các cập nhật phụ thuộc trạng thái, cần thiết kế thứ tự xử lý theo vị thế hoặc aggregate.

**Outbox hôm nay chỉ bảo vệ việc phát `ExecutionApplied`.**

Nó chưa tự giải quyết:

- Lệnh đã lưu nhưng chưa chuyển tới matching.
- Khôi phục sổ matching trong bộ nhớ.
- Nhiều publisher hoặc nhiều worker.
- Mọi tác dụng bên ngoài MySQL.

Không đánh dấu những khả năng đó đã hoàn thành chỉ vì có bảng outbox.

**13. Kiểm thử bắt buộc**

| Kiểm thử | Kết quả |
|---|---|
| Source transaction rollback | Không có event outbox đã commit |
| Outbox insert thất bại | Toàn bộ execution rollback |
| Worker chưa chạy | Event vẫn nằm bền trong MySQL |
| Worker restart | Đọc lại event từ database |
| Consumer commit, worker chưa mark | Giao lại không tạo tác động mới |
| Duplicate source execution | Không tạo thêm outbox |
| Retry delivery | Giữ nguyên eventId và payload |
| Consumer thất bại trước commit | Marker và projection rollback |
| Hết retry | FAILED, quan sát và xử lý được |
| Worker chạy chậm | Không có các vòng poll chồng nhau |
| Market Clock cố định/tương lai | Không làm worker chờ sai |
| Chỉ chạy consumer | Không sửa tài sản nguồn |

```text
- Giữ eventId và payload.
- Lỗi tạm thời retry.
- Schema sai/conflict hoặc hết retry chuyển FAILED.
- Nếu crash sau tăng attemptCount, lần sau vẫn xử lý được
  trường hợp hết ngân sách, không bỏ event PENDING vĩnh viễn.
- FAILED không bị xóa.
- Nếu thêm manual retry, chỉ OPS,
```
